# Volunteer codebase audit

Reviewed application source at `cd8597b` and read `CODEBASE_MAP.md` from the documentation branch first. The locally known `origin/main` at `65b0538` differs only by that map. Impact 3 means possible data exposure, service disruption, or material loss. Impact 2 means meaningful operational or development disruption. Impact 1 means localized friction. Effort 1 is under an hour, 2 is roughly half a day to two days, and 3 is several days or a coordinated rollout. Effort excludes waiting on approvals.

The Slack match at historical `2d1542b:docs/SLACK_SIGNUP_NOTIFICATIONS.md:36` is presented as an example [redacted]. The test fixture at `tests/helpers/test-helpers.js:17` is a hardcoded test value [redacted]. No live credential was confirmed. Custom formats, binary artifacts, and commits outside local refs are outside that finding. No dedicated secret scanner was installed. The browser reads the public Supabase project URL and anon key at `src/lib/supabaseClient.js:3–4`. The anon key is intended for browser use and depends on RLS for data protection. No privileged key literal was identified in tracked frontend source. Generated bundles were unverified. No `eval`, `dangerouslySetInnerHTML`, Svelte `@html`, or direct `innerHTML` matches were found in the inspected app, Edge Functions, and Apps Script source. Several functions allow all origins. Evaluate their authorization and abuse controls independently of CORS.
2. **Build and deploy.** Checked the documented fresh-clone sequence against the lockfile, configuration, and tracked files. It breaks at the missing environment template, and its stated Node version is incompatible with the locked Vite release. The build and a fresh Supabase deployment were unverified. Installing and building would write files beyond this audit's single-file scope. No tracked frontend deploy script that removes production assets was found. Hosted configuration and destructive manual SQL are separate risks.
3. **Silent failures.** Traced signup, waiver, clinic, communications, auth, and scheduled paths. Console logs and GitHub Actions failure handling exist. External alerting and delivery monitoring are unverified. No payment handler was identified in the inspected paths.
4. **Development drag.** Ranked tracked paths by commit frequency and measured source size. Checked import references and TODO/FIXME markers. No TODO/FIXME cluster was found in `src`, `supabase`, or `tests`. Knip and depcheck were unavailable. Dependency removal candidates remain unverified unless supported by import evidence.

## Proposed PR sequence

1. **Security containment.** Remove the default admin recipe. Add isolated access checks and harden profile access, the contacts directory, and generic email relay boundaries as separate security commits or narrowly scoped security PRs. Coordinate any live restriction with the environment owner and verify organizer and volunteer workflows.
2. **Regression tests and CI.** Replace stale auth coverage with tests against the active routes. Add isolated roster, permission, waiver, delivery, and clinic tests before shared workflow changes.
3. **Security and signup integrity.** Use separate security PRs for login-mail abuse controls and registration identity. Follow with a data-integrity PR for transactional capacity, waiver persistence, and idempotent retries.
4. **Reproducible environments and dependency patches.** Document and verify baseline migrations, runtime, environment names, and independent deploy steps. Patch dependencies in a separate PR with build and PDF-export smoke checks.
5. **Cleanup and refactor.** Keep generated files and obsolete scaffolding in a cleanup PR. Consolidate roster logic only after the regression tests pass. Track delivery visibility separately.

## Five-line summary

1. Profile policy and public directory access are the highest data-exposure risks. Live grants still need verification.
2. The generic email relay lacks function-side authorization, putting delivery quota and sender reputation at risk.
3. Signup can confirm a roster entry without reliably recording required waiver consent or enforcing capacity.
4. First PR to open is security containment for profile access, the public directory, and the default admin setup, with access checks.
5. Follow with a dedicated email security PR and add signup regression tests before restructuring the workflow.
